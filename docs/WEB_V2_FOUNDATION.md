# Web v2: основа продукта

## Зафиксированная отправная точка

- Проверенная настольная версия закреплена тегом `desktop-v1.0.5`.
- Веб-продукт развивается только в ветке `web-v2`.
- Алгоритмы расписания, проверки накладок и DOCX сохраняются как проверенное ядро до завершения переноса данных.

## Первый сценарий для пилота

1. Администратор сервиса создаёт организацию и выдаёт пользователю логин и временный пароль.
2. Пользователь входит, при первом входе меняет пароль и видит срок пробного доступа.
3. Все расписания и справочники доступны только участникам этой организации.
4. Пользователь завершает работу кнопкой «Выйти»; сервер отзывает сессию.
5. По окончании пробного срока данные сохраняются, но изменение расписаний блокируется до активации оплаченного доступа.
6. После оплаты администратор сервиса продлевает доступ организации. Автоматизацию платежей можно подключить после проверки пилота.

## Граница компонентов

```text
Браузер
  -> вход / выход / текущий пользователь
  -> проверка доступа организации
  -> API расписаний с обязательным organization_id
  -> PostgreSQL
       организации, пользователи, роли, сессии, доступ, аудит
       программы, периоды, темы, занятия и справочники организации
```

Браузер никогда не определяет сам, действует ли пробный или оплаченный доступ. Это решение принимает сервер на каждом защищённом запросе. В базе хранится только хеш токена сессии, а пароль хранится как `scrypt`-хеш с отдельной случайной солью.

## Первая схема PostgreSQL

- `organizations` — учреждение и его состояние.
- `users` — выданные учётные записи; логин уникален и нормализуется сервером.
- `organization_members` — принадлежность к учреждению и роль: владелец, администратор, составитель расписания или просмотр.
- `organization_access` — пробный срок, оплаченный период, льготный срок и блокировка.
- `sessions` — отзываемые серверные сессии с ограниченным сроком действия.
- `audit_events` — входы, выходы, выдача доступа и значимые изменения данных.

Все будущие таблицы расписаний получают обязательный `organization_id`. Запрос без контекста организации считается ошибкой; перед выпуском дополнительно включается PostgreSQL Row Level Security как второй уровень защиты.

## Порядок реализации

1. **Основа — выполнено в первом коммите `web-v2`.** Схема организаций, пользователей, доступа, сессий и аудита; хеширование пароля; токены сессии; единое правило срока доступа; модульные тесты.
2. Добавить миграции PostgreSQL и репозитории для входа, выхода, текущего пользователя и выдачи учётной записи администратором.
3. Закрыть API расписаний проверкой сессии и организации; временный SQLite-диспетчер не публиковать как многопользовательский API.
4. Перенести таблицы расписаний в PostgreSQL, сохранив интерфейс проверенного ядра и добавив `organization_id` во все ключи и запросы.
5. Добавить страницы входа, смены временного пароля, окончания пробного срока и управления пользователями организации.
6. Создать однократный импорт настольной `.db` в выбранную организацию с предварительным отчётом, контрольными суммами и сверкой количества записей.
7. Развернуть пилот: HTTPS, резервные копии, журналирование, ограничение попыток входа и мониторинг.

## Критерии готовности пилота

- Пользователь другой организации не может прочитать или изменить чужие данные даже при подмене идентификатора в запросе.
- Выход немедленно отзывает текущую сессию; истёкшая сессия не продлевается клиентом.
- Пробный срок и оплаченный срок вычисляются только по серверному времени.
- После окончания доступа данные не удаляются, экспорт и обращение к администратору остаются доступны согласно выбранной коммерческой политике.
- Импорт реальной базы даёт те же программы, темы, периоды, занятия и справочники, что проверенная 1.0.5.
- Автозаполнение, накладки и DOCX проходят набор сравнительных тестов с `desktop-v1.0.5`.
