# Самостоятельная регистрация демо

Посетитель нажимает «Попробовать демо» на странице входа, вводит название
организации, имя, уникальный логин и пароль. Создается отдельная организация,
пользователь с ролью `scheduler` и собственные стартовые примеры расписания.
После создания интерфейс выполняет обычный вход через существующую сессию.
Если вход не удался, можно войти с выбранными данными без повторной регистрации.

Срок доступа — ровно 7 суток от серверного времени создания; хранение данных —
еще 30 суток после окончания. Эти сроки, роль и организация не принимаются от
посетителя. Повторный нормализованный логин возвращает 409 и не продлевает демо.
При потере ответа интерфейс сообщает, что аккаунт мог уже появиться, и предлагает
проверить вход. Уникальный индекс логина и транзакция не допускают частичного
создания второй организации при конкурентном повторе.

`POST /api/auth/register-demo` принимает только JSON с полями `organizationName`,
`displayName`, `login`, `password`, необязательным пустым `website`. Пароль имеет
10–256 символов; логин — 3–100 букв, цифр либо `. _ @ -`, после NFKC,
обрезки пробелов и перевода в нижний регистр. `website` — поле-ловушка для ботов.
Ответ содержит идентификаторы, логин и сроки, без пароля, хеша или служебного токена.
Пользователь получает права составителя расписаний только своей организации.

## Ограничения и защита

- Флаг `DEMO_PUBLIC_REGISTRATION_ENABLED` по умолчанию выключен; только точное
  значение `true` включает регистрацию, причем только в режиме PostgreSQL.
  `/api/runtime` сообщает браузеру только булево значение `demoRegistrationEnabled`.
- Тело регистрации ограничено 8 KiB до общего парсера документов; иные форматы
  отклоняются до большого парсера. Чужой Origin и cross-site fetch запрещены.
- 5 запросов в час с одного IP, 30 запросов в минуту суммарно, максимум
  2 одновременные регистрации на процесс. Попытка резервируется до вычисления
  хеша; ошибки и успешные запросы учитываются одинаково. Ответ 429 имеет Retry-After.
- Не более 50 созданных организаций за последние 24 часа. Проверка и создание
  сериализуются PostgreSQL advisory lock в одной транзакции; счетчик — события
  `demo.self_registered` в существующем аудите. Перезапуск сервера его не сбрасывает.
- Организация, пользователь, членство, демосрок, аудит и стартовые данные
  фиксируются одной транзакцией. Существующие пользователи не меняются.
- Административные маршруты и `node ./scripts/create-demo-account.mjs` сохранены.
  `DEMO_ADMIN_TOKEN` не передается в frontend и для открытой регистрации не нужен.

IP-лимиты и общий предел попыток хранятся в ограниченной памяти процесса и
сбрасываются при рестарте. В одном процессе — 5 попыток/IP/час, 30 попыток/минуту
суммарно и 2 незавершенные регистрации. При нескольких процессах эти пределы
умножаются; суточная квота созданий остается общей для одной PostgreSQL.
Без подтверждения почты несколько логинов могут принадлежать одному человеку.
Нападающий с реальными разными IP может занять все 50 мест и закрыть новые
регистрации до освобождения скользящего окна. Квоты ограничивают рост БД и работу
приложения, но не обещают доступность при распределенной атаке. Платных сервисов нет.

### Граница доверия Render и безопасный источник IP

Для регистрации development использует только адрес сокета и игнорирует все
forwarding-заголовки. В production поддержан существующий публичный бесплатный
Render web service: нужны автоматически заданные `RENDER=true` и непустой
`RENDER_EXTERNAL_HOSTNAME`. Ключ IP берется только из `CF-Connecting-IP`,
проверяется `net.isIP` и канонизируется (включая IPv6). Отсутствующий/некорректный
адрес, список адресов либо неподдержанная production-среда дают 503 до хеширования
пароля и обращения к БД. Fallback на XFF отсутствует.

[Официальная статья Render](https://render.com/articles/host-pocketbase-on-render)
прямо описывает перезапись `CF-Connecting-IP` на публичном Cloudflare edge и
предупреждает о присланном клиентом левом XFF. [Переменные Render](https://render.com/docs/environment-variables)
позволяют распознать web runtime; [бесплатные web services](https://render.com/docs/free)
не принимают входящий private-network трафик и имеют один экземпляр.
Контейнерный порт не публикуется напрямую. Поэтому в текущем бесплатном публичном
сервисе не требуется угадывать число XFF-переходов или подключать отдельный proxy.
Настройка `trust proxy = 1` приложения сохранена для протокола/cookie, но не
определяет корзину регистрации. При переносе на private service, платный сервис
с private ingress, иной hosting или дополнительный gateway сначала пересмотреть
границу доверия; не подменять `RENDER` вручную и не включать `trust proxy = true`.

### Суточный лимит и транзакции нескольких процессов

Каждая публичная регистрация открывает явную `READ COMMITTED` транзакцию и
пытается взять `pg_try_advisory_xact_lock(731842, 1)`. Занятая блокировка дает
429 `registration_busy`, `Retry-After: 10`, без ожидания и без создания данных.
После получения блокировки отдельный SQL-запрос считает события
`demo.self_registered` за последние 24 часа по часам PostgreSQL
`statement_timestamp()`. Время нового события тоже задает PostgreSQL, поэтому
смещение часов процессов не обходит квоту. Некорректный результат счетчика
закрывает регистрацию. При 50 событиях ответ — 429 `registration_capacity`.

Блокировка действует между всеми процессами/подключениями к одной базе и
освобождается PostgreSQL при commit/rollback. Благодаря `READ COMMITTED` следующий
успешный владелец видит предыдущий commit. При 49 событиях параллельные процессы
могут создать максимум одну новую организацию; занятый процесс при повторе увидит
50 и получит отказ. Организация, пользователь, членство, доступ, аудит и стартовые
данные коммитятся вместе. Сбой наполнения или уникальности логина откатывает все
и не расходует место. Обычная очистка удаляет организацию через 37 суток, поэтому
не удаляет счетчик текущего 24-часового окна. Ручные DBA-изменения аудита, разные
базы или обход этого маршрута административным CLI не входят в публичную квоту.

Лимит считает успешные создания, а не попытки или объем HTTP-трафика. Расход CPU
до БД ограничен отдельными пределами процесса; Render edge дополняет их сетевой
защитой. При росте аудита следует оценить индекс по типу события/времени. Реальный
сбой соединения с БД может задержать запрос до сетевого таймаута существующего
пула; глобальная конфигурация пула этой функцией не менялась.

## Выкладка и отдельное включение

Из `render.yaml`: бесплатный Docker web service `schedule-automator-demo`,
Frankfurt, Dockerfile в корне, health check `/api/healthz`, autoDeployTrigger `off`.
Docker собирает API и Vue и запускает
`node --enable-source-maps artifacts/api-server/dist/index.mjs`.
Привязка реального Render-сервиса к репозиторию и ветке окончательно не указана
в локальных файлах: перед публикацией сверить ее в панели владельца.

Новая миграция схемы для регистрации не требуется: используются существующие
таблицы организаций, пользователей, членств, демодоступа и аудита.
Обычный startup по-прежнему применяет существующие миграции проекта.

Только после отдельного подтверждения конкретных действий:

1. Опубликовать проверенный commit нужной ветки в привязанном репозитории и
   вручную развернуть именно этот commit в существующем бесплатном сервисе.
   Тариф, БД, секреты и `REQUIRE_RESTRICTED_DATABASE_ROLE` не менять.
2. С выключенным флагом проверить `/api/healthz` и `/api/runtime`:
   `demoRegistrationEnabled=false`, `demoRegistrationAddressReady=true`,
   кнопка отсутствует, endpoint закрыт. Поле готовности не раскрывает адрес IP,
   заголовки или секреты. Повторить только GET runtime с присланными клиентом
   `CF-Connecting-IP: invalid` и произвольным XFF: публичный Render edge должен
   заменить CF-заголовок, поэтому приложение по-прежнему сообщит готовность
   (либо edge отклонит запрос). Если обычный GET дает `false`, остановиться:
   не включать флаг и не добавлять fallback на XFF.
3. Отдельно согласовать и установить в этом сервисе ровно
   `DEMO_PUBLIC_REGISTRATION_ENABLED=true`, затем выполнить требуемый Render
   перезапуск/выкладку конфигурации. Не помещать служебный токен в VITE-переменные.
4. Проверить видимость формы и исправленный контакт
   `@SyncMaster30001` / `https://t.me/SyncMaster30001`. Тестовые реальные учетные
   записи на production создавать только по отдельному разрешению.

## Воспроизведение живых локальных проверок

`scripts/registration-postgres-integration.mjs` запускается отдельно от обычных
unit-тестов. Он принимает только явный passwordless loopback URL на высоком порту,
проверяет фактический `data_directory` временного кластера в Temp, создает новую
базу с маркером и отдельные роли владельца и приложения. Унаследованный
`DATABASE_URL` не используется. Пример для уже установленного тестового кластера:

```powershell
node scripts/registration-postgres-integration.mjs --admin-url postgresql://schedule_test_owner@127.0.0.1:57253/postgres --cluster-data-dir C:\Users\storm\AppData\Local\Temp\schedule-postgres-test\data
```

Проверены все существующие миграции, фактические 14 forced-RLS политик,
ограниченная DB-роль, разделение организаций через dispatcher и SQL, откат
регистрации, HTTP login/me/logout, граница 7 суток и два независимых процесса
Node с одним оставшимся местом квоты. Результат сохраняется без паролей,
хешей и session token. Тестовые объекты остаются только во временном кластере;
после проверки он остановлен. Новых миграций для данной функции нет.

Отключение: убрать флаг или установить `false` и перезапустить сервис.
Это закрывает новые регистрации; существующие учетные записи сохраняются.
